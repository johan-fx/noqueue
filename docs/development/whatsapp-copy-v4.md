The checked-in staging configuration selects **cloud V4 with sending enabled and open recipients**. There is no later internal approval or activation step: the operator checks actual provider approval before creating new test turns. This configuration does not prove deployment or delivery. The ES/EN catalog defines exact bodies, ordered body parameters, STOP/BAJA footer, buttons, environment-specific names, and bindings. V1–V3 copy and snapshots remain unchanged; absent an explicit profile, the server default remains V2. The local sandbox path sends a plain-text preview with modeled button labels, not custom V4 templates or native interactive buttons.

## Staging setup and testing

1. Review `apps/api/src/integrations/whatsapp-copy-v4.ts` (`whatsappV4Catalog`) as the registration manifest. It contains **38 registrations**: 12 logical variants × two locales, with seven URL-bearing variants registered separately for staging and production. Each waiting template uses one nonempty `wait` parameter; an unknown ahead count is omitted from that value rather than sent as a blank placeholder. Register the exact body, footer, ordered parameters/examples, and button layout from each entry; use `es_ES` and `en_US`. Never register a whole-body variable.
2. Every navigation is a native URL button, never an inline body URL. Turn buttons use `https://staging.noqueue-app.com/t/{{1}}` or `https://noqueue-app.com/t/{{1}}`; their dynamic suffix is `<recovery-token>?lang=<locale>&source=whatsapp&notice=<notice-id>`. Selector buttons use the matching environment's `/v/{{1}}` pattern and the suffix `venueId?lang=<locale>&source=whatsapp`. The selector presents available lists; it never automatically reenrolls a customer. URL-bearing templates have `_staging` or `_production` in their names. The existing per-variant/per-locale binding key maps to that environment's exact template name; configure values separately per deployment without changing activation flags.
3. Deploy only after the separately authorized environment preflight in `docs/runbooks/deployment.md`: credentials, phone ID, authenticated callback, migrations and backlog cutoff must be verified. Staging already selects `WHATSAPP_COPY_VERSION=4` and `WHATSAPP_ENABLED=true`. No recipient allowlist or operator approval flag is required for valid V4 staging messages. Exact bindings, the staging origin, valid user consent/current notice version and signed action context remain mandatory. `WHATSAPP_ENABLED=false` remains an emergency stop.
4. The operator confirms actual provider approval, wording, parameter/button order, URL prefixes and category, then creates **new turns**. No configuration change or redeployment is needed after approval. A definitive provider rejection leaves the committed turn intact and records a failed notification; do not revive that notification automatically or fall back to V1–V3. Unknown delivery outcomes are never blindly retried. Until the provider accepts and delivery callbacks arrive, delivery is unverified.

The open policy requires exactly `APP_ENV=staging`, `WHATSAPP_MODE=cloud` and `WHATSAPP_COPY_VERSION=4`. It does not extend to local, sandbox, production or historical V1–V3 messages. Production still requires `STAGING_CONSENT_APPROVED=true`, `WHATSAPP_V4_TEMPLATES_APPROVED=true`, exact production bindings and its existing recipient policy; no production deployment is defined here. The old confirmation experiment stays disabled and is not the real V4 queue flow.

All templates use the fixed locale footer in the catalog: “Envía BAJA para dejar de recibir avisos.” / “Reply STOP to stop receiving updates.” Parameter examples are fictional; use the manifest examples in the listed order. Text is fixed around sequential placeholders, not replaced with an entire-body variable. Fixed-body `*...*` markers identify WhatsApp bold spans; formatting markers stay in the template body, never in a dynamic parameter. The `wait` parameter contains only the available position and estimate sentences, not the whole message. It is bolded as one information chunk, a deliberate minimal adaptation from Figma's finer emphasis so the body avoids adjacent dynamic parameters. Unknown position text is omitted, and an unknown estimate is never rendered as zero. Paste the exact body, including its literal asterisks, into the visual template editor; its preview renders the enclosed phrases in bold and hides the delimiter characters. Do not strip the asterisks from the body. Body URL placeholders are not used: every turn or selector URL is attached to a native button. Body placeholders retain fixed words after the final parameter, never a dangling parameter. 360dialog's [template guidance](https://docs.360dialog.com/docs/resources/templates) describes parameter placement requirements; keep fixed text between parameters and avoid a leading or trailing parameter.

360dialog documents asterisks for bold formatting in WhatsApp text messages. The template provider still controls approval; registration is documented above but approval is not claimed. See [360dialog formatting in text messages](https://docs.360dialog.com/docs/messaging/overview).

V4 uses at most three buttons per template and at most one URL button in the current catalog. Where actions and navigation share a template, the grouping is the two ordered quick replies followed by the URL button, matching 360dialog's supported template grouping. Quick replies are “Pasar turno” then “Abandonar la lista” / “Pass my turn” then “Leave the list”; they carry opaque, signed server payloads, and button titles are never command authority. URL labels fit the provider's 25-character template limit. Native actions apply on one tap; the direct result is a separate service-window reply (text for yield, selector CTA for cancellation), not another template or confirmation prompt.

The successful WhatsApp cancellation result uses a **standalone interactive `cta_url`** selector, separate from the approved template URL button. Its short labels are “Elegir lista” / “Choose a list”. The 360dialog standalone CTA reference documents the payload shape but not a display-text limit; the sender therefore enforces a conservative 20-character maximum, matching 360dialog's documented limit for interactive carousel URL-button labels. Do not apply that 20-character conservative sender rule to template URL buttons; those use the template-specific 25-character limit. See 360dialog's [standalone CTA URL](https://docs.360dialog.com/docs/messaging/message-types/interactive/call-to-action-url-button), [interactive carousel](https://docs.360dialog.com/docs/messaging/message-types/interactive/media-carousel), and [template elements](https://docs.360dialog.com/docs/resources/templates/template-elements) references.

## Copy and lifecycle rules

- `venue` is the establishment name; `resource` is the assigned service/resource fallback. Do not substitute the service label for the establishment name.
- `wait` is one nonempty parameter composed from the available ahead and ETA sentences. Its wording handles zero, singular, and plural counts; unknown ahead is omitted without an empty placeholder, and unknown ETA remains explicitly unknown rather than zero.
- `improved_wait_recommended` is still a waiting party and never claims a resource is available. `improved_ready` is used only when an actual call beats the last accepted absolute forecast by the configured material threshold. A better waiting ETA alone never means “ready”.
- No verified venue timezone is available for rendering an exact local arrival clock. Ready copy links to the turn screen for its authoritative arrival deadline instead of calculating a moving “next N minutes” at dispatch. The retry body and parameter snapshot therefore do not change as time passes.
- Joined notices have a turn URL button; delayed notices have no buttons. Ready templates preserve the two action quick replies and add the turn URL button. Only a WhatsApp-origin yield receives a direct result; web yield, normal arrival, and completion do not create a WhatsApp message. Customer cancellation/expiry uses the selector CTA; staff/unknown cancellation uses the turn-status CTA.
- Selector navigation preserves `lang` and `source=whatsapp`, presents currently available lists, and never automatically reenrolls a customer.
- Direct action-result replies are bound to the authenticated inbound event and its phone/context, and are sent only inside the 24-hour user service window. A requested result after STOP does not restore consent or permit proactive notices; no free-form reply is sent outside the service window.

## Durable compatibility and fail-closed behavior

- V4 remains an additive copy profile. An absent `WHATSAPP_COPY_VERSION` still means V2; accepted explicit values are 2, 3, and 4. An invalid explicit value fails closed.
- Copy version, variant, and signed action lifecycle context are frozen in the existing outbox snapshot at creation. Dispatch/retry uses that frozen snapshot rather than the current profile. Existing V1–V3 snapshots are never reinterpreted. No database migration is required.
- The provider template name, layout, and catalog revision are not frozen in those V4 snapshots. Before the enabled staging deployment, inventory pending rows and explicitly cancel only identified pre-cutover intents that must not send, retaining their rows and trace evidence. Do not delete entries/history or reset terminal, sending or unknown outcomes. Older V1–V3 snapshots retain their original policy and rendering; do not reinterpret them. Do not assume byte-identical V4 rendering across source upgrades.
- New admission checks the complete selected-locale and selected-environment V4 catalog. Cloud dispatch independently checks its selected binding. Operator approval flags remain required outside open cloud V4 staging; they are declarations, not live provider status queries. Recipient expansion at dispatch applies only to a validated frozen V4 lifecycle snapshot or a validated V4 action-result snapshot, never just the current profile. Quick-reply sends require server-generated action payloads; selector URL sends require venue context, while turn URLs use the signed recovery token and notice ID. A missing prerequisite is not silently downgraded.
- The existing durable webhook row stores inbound action payload and provider context before acknowledgment. The serialized queue command atomically commits the command, events, processed inbound event, and one deduplicated result intent. Invalid sender/context/signature, expired lifecycle, phase/call-cycle mismatch, and duplicate actions cannot perform another mutation.
- STOP cancels proactive notices but does not discard an already-authorized, exact event-bound result intent. The exception does not clear STOP or reopen consent.
